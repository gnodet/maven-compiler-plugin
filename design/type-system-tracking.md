# Type System Tracking

This document describes how the incremental compilation engine tracks type references,
including generic types, across the dependency graph.

## Generic type argument tracking

JVM descriptors are erased: `List<Foo>` appears as `Ljava/util/List;` — `Foo` is invisible.
Generic type arguments are preserved only in the bytecode `Signature` attribute.

`ClassfileClassAnalyzer` parses the JVM generic signature string (JVMS §4.7.9.1) via a
recursive descent parser (`addGenericSignatureRefs` → `parseSig` / `parseClassTypeSignature`)
and adds all concrete class references to the target type set.

### Where signatures are parsed

- The class `Signature` attribute → covers `extends AbstractList<Item>`,
  `implements Comparable<Foo>`, etc.
- Each non-private field's `Signature` attribute → covers `List<Foo> items`,
  `Optional<Bar> opt`
- Each non-private method's `Signature` attribute → covers `List<Foo> getItems()`,
  `Map<K,V> getMap()`

### Supported constructs

| Construct | Example | Result |
|-----------|---------|--------|
| Simple type args | `Ljava/util/List<Lcom/example/Foo;>;` | `com.example.Foo` |
| Multiple args | `Ljava/util/Map<Lcom/example/Key;Lcom/example/Val;>;` | `Key`, `Val` |
| Wildcard bounds (`+`/`-`) | `+Lcom/Foo;` | `com.Foo` |
| Unbounded wildcards (`*`) | — | Skipped |
| Type variables (`TT;`) | — | Skipped (not a concrete dependency) |
| Arrays | `[Lcom/Foo;` | `com.Foo` |
| Inner class suffixes | `.InnerName` | Outer class extracted; inner suffix skipped |
| FormalTypeParameter bounds | `<T extends MyBound>` | `MyBound` extracted |
| Multiple type params with bounds | `<A, B extends Foo, T extends Bar>` | All bounds extracted |

### FormalTypeParameter vs TypeVariableSignature — critical grammar distinction

The JVMS grammar has two distinct constructs that look similar but are parsed differently:

- **TypeVariableSignature:** `T Identifier ;` — a *reference* to an existing type variable.
  Not a concrete dependency — skip.
- **FormalTypeParameter:** `Identifier ':' ClassBound {'::' InterfaceBound}` — a *declaration*
  with bounds. The bounds ARE concrete dependencies.

The parser uses an `inFormalTypeParams` flag (passed to `parseSig`). When `true` (inside a
`<...>` block at the top level of a class/method signature), the grammar is
`Identifier ':' Bound*`. When `false` (inside type arguments of a class like `List<Foo>`),
`T` at the start means TypeVariableSignature.

### Overconsume pitfall

Calling `parseSig(sig, pos, types, false)` to parse a single bound's `FieldTypeSignature`
is incorrect — `parseSig(false)` loops until end-of-string, consuming subsequent type
parameters. Result: `<K:Lfoo/Foo;T:Lbar/Bar;>` → `Foo` collected, `Bar` missed.

Fix: dispatch directly to `parseClassTypeSignature` (for `L`), inline skip for arrays and
type variables — each call consumes exactly one `FieldTypeSignature`.

This does NOT affect the ABI fingerprint (that already stores the full signature string
verbatim) — only the cascade graph.

## Sig/impl split from bytecode

`ClassfileClassAnalyzer` extracts two categories of type references from `.class` files:

- **`signatureTypes`:** Non-private field/method descriptors, class-level annotations
  (part of the API surface)
- **`implementationTypes`:** Private member descriptors, bytecode instructions (INVOKE*,
  NEW, CHECKCAST, field owners), constant pool class entries

### Bridge method handling

`collectTypes()` must use `isPrivateOrSynthetic()` for **both** fields and methods. Bridge
methods (generated by javac for generics, covariant returns) must be excluded from the
public API surface. Using only `isPrivate()` for classification creates an asymmetry:
bridge methods are excluded from the canonical ABI form but their descriptor types would
falsely appear in `signatureTypes`.

### Annotation type tracking

Annotation types are tracked separately in `annotationTypes` for processor cascade.
JDK annotations (`@Deprecated`, etc.) are filtered via `isJdkType` before they reach
`annotationTypes` from `signatureTypes`.

## `BytecodeAnalyzer.ClassAnalysis` record

```java
record ClassAnalysis(
    Set<String> signatureTypes,
    Set<String> implementationTypes,
    Set<String> annotationTypes,
    String moduleName,
    boolean isModuleInfo
)
```

The record carries `sourceFileName` for source → class mapping.

### `Set.copyOf()` on record fields

When constructing a `ClassAnalysis` whose fields are `Set<String>`, mutable builder sets
must be wrapped with `Set.copyOf()`. `ClassAnalysis` is consumed by many callers — a leaked
mutable `TreeSet` allows stray mutation that silently corrupts fingerprint computation on
the next cascade pass.

## Annotation processor classification

Annotation processors are classified via a resource file at:

```
META-INF/maven/compiler/incremental.annotation.processors
```

Format: one line per processor, `fully.qualified.Name,TYPE`. Valid types: `ISOLATING`,
`AGGREGATING`, `UNKNOWN`. Maven reads this path first; the Gradle convention
`META-INF/gradle/incremental.annotation.processors` is also read as a fallback.

- **ISOLATING:** Safe for per-file recompilation — output depends only on its input source.
- **AGGREGATING:** Output depends on all sources — requires full rebuild when activated.
- **UNKNOWN:** Conservative — treated as aggregating.
